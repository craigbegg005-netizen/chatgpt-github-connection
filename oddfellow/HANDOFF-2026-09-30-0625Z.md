## ⚠️ 1. The blueprint requires `rootDir: oddfellow` but pinned no branch

`main` is an index only: `git ls-tree origin/main` returns **`.gitignore` and `README.md`** and
**no `oddfellow/` directory**. A service pointed at `main` therefore **cannot satisfy
`rootDir: oddfellow`**, and its build fails with no obvious cause from outside — which is exactly
the shape of what we are seeing (TCP accepted, no HTTP response).

**Ask whoever holds Render access: what branch is `oddfellow-letta-backend` set to?** If it is
`main`, that is the bug. It must be `letta/combined-single-service-v0.20.4`. I have now pinned
`branch: letta/combined-single-service-v0.20.4` in `render.yaml` so this cannot recur on a
blueprint sync. `a652c55`

## ⚠️ 2. `autoDeploy: false` means a push never deploys, and saving env vars is not a deploy

This is deliberate — one AI deploys at a time, and a surprise deploy mid-change is worse than a
manual click — but its consequence was undocumented and is worth stating plainly:

> **Pushing to the branch does not update what is running, and saving env vars is not by itself a
> deploy. Bringing this service up requires an explicit deploy in the Render dashboard.**

So if the secrets were saved and nothing else was clicked, **no new deploy was triggered.** That
alone would leave the service with no successful deploy and therefore no instance to serve.

**Concrete ask: trigger a manual deploy** (Render → `oddfellow-letta-backend` → Deploy → Deploy
latest commit) and read the Events/Logs. That single action distinguishes all three possibilities
I listed at the top of this handoff.

## 3. The fallback deploy path had silently drifted a version behind — fixed

While Render was blocked I verified the fallback instead of idling. `./deploy.sh verify` (local
Worker, no account needed) failed its own gate 0:

# Addendum 07:45 UTC — the 502 is NOT the secrets, and I can prove it

## What changed

At ~07:30 UTC the deploy target stopped being silent: `/livez` returned **Render's own 502 error
page** (HTML, ~10s) instead of no response at all. It has since gone back to no response. A 502
from Render's edge means the router is now reaching for the service but **no healthy instance is
behind it** — the application is not running.

## ⚠️ This rules the secrets out as the cause of a 502, and that is testable

`LETTA_API_KEY` and `ODDFELLOW_OWNER_TOKEN` are read as
`os.environ.get(..., "").strip()` and **nothing raises at import**. The app is designed to start
without them and report readiness separately. I verified that directly, on this machine, with
**both secrets empty**:

```
/livez    HTTP 200  {"live":true,"ready":false,
                     "checks_failed":["LETTA_API_KEY","ODDFELLOW_OWNER_TOKEN","LETTA_MODEL"],
                     "version":"0.20.6"}
/healthz  HTTP 503  {"ok":false,"checks_failed":[...]}
```

**So: missing secrets produce a running app that answers `/livez` with 200 and `/healthz` with 503.
They cannot produce a 502.** A 502 means the process never came up.

**Therefore the investigation should move off the credentials and onto the build and start:**

1. **What branch is the service set to?** If `main`, `rootDir: oddfellow` does not exist there and
   the build cannot succeed. This is still my leading candidate.
2. **What does the build log say?** `pip install -r requirements.txt` runs in `oddfellow/`.
3. **What does the start log say?** `uvicorn oddfellow_letta_backend:app --host 0.0.0.0 --port $PORT`.
   A 502 with no instance is what a crashed start command looks like.
4. **Was a deploy actually triggered?** `autoDeploy: false` means a push never deploys.
