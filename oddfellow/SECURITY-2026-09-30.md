# Security note — 2026-09-30 — owner token exposure in the front end

**Author:** Oddfellow (Letta agent, `agent-a9a8eb2c-2fed-4554-9998-aa4783c7efc4`)
**Status of the fix:** 🧪 TESTED in a real browser, then 🛠 IMPLEMENTED in the
deploy branch. Not yet deployed — nothing is deployed until the Render service
exists.

## What was wrong

`oddfellow/frontend/index.html` stored the owner token in `localStorage`:

```js
localStorage.setItem(BKEY, JSON.stringify({url: backend.url, token: backend.token}))
```

while the same page loaded a **third-party script** at the top of `<head>`:

```html
<script src="https://js.puter.com/v2/"></script>
```

`localStorage` is readable by **any** script running in the origin. So a
compromised, hijacked, or simply changed `js.puter.com` could read the owner
token. That token is not a display preference: it authorises reading the owner's
conversation history and sending messages as the owner through the backend, which
in turn acts on the owner's Letta account.

The exposure was not theoretical-but-unreachable. It was the default state of the
page on every load, with no user action required.

## What was changed

Two changes, both in the front end, plus the audit trail below.

**1. The Puter SDK is loaded lazily.**

The eager `<script>` tag is gone. `ensurePuter()` injects it on first use:

```js
let puterPromise = null;
function ensurePuter(){
  if(window.puter) return Promise.resolve(window.puter);
  if(puterPromise) return puterPromise;
  puterPromise = new Promise((resolve, reject) => { /* inject, resolve, reject */ });
  return puterPromise;
}
```

Every former `puter.*` call site now goes through it. `accountRefresh()` is
explicitly guarded so that refreshing a status chip never loads the SDK. And the
boot path skips the local-router discovery entirely once a backend has been
configured — so **with a backend configured, the third-party script is never
loaded at all.**

**2. The owner token is not written to disk by default.**

It is held in memory for the session. Persisting it is an explicit opt-in
("Remember on this device", default off). If the Puter SDK is loaded while the
opt-in is on, the opt-in is **revoked** and the owner is told, in the transcript,
exactly why:

> The Puter SDK is a third-party script and can read this page's storage, so
> Oddfellow has stopped remembering your owner token on this device. It stays in
> memory for this session only. Leave the account disconnected to keep it
> remembered.

## Evidence — real browser, 2026-09-30 02:22–02:24 UTC

Chrome via CDP against a local v0.20.5 with `ODDFELLOW_FRONTEND_DIR=frontend`.
Each line is a read-back from the page, not an expectation.

| Step | Observed |
|---|---|
| First load, no backend configured (local mode) | `js.puter.com/v2/` **is** loaded — correct, the free-only local router needs it |
| `localStorage` on that load | `{}` — nothing stored |
| Backend URL + token entered, "Remember" **off** | stored record is `{"url":"http://127.0.0.1:8107","remember":false}` — **no token** |
| Reload with a backend previously saved | resources matching `puter` → **`[]`**; chip reads `Backend: token needed` |
| "Remember on this device" ticked, token entered | stored record is `{"url":…,"remember":true,"token":"…"}` — opt-in works |
| "Connect account" clicked (loads the Puter SDK) | stored record drops back to `{"url":…,"remember":false}`; checkbox unticks; the security message above appears in the transcript |

Screenshot of the final state: `oddfellow/evidence/token-security-verified.png`.

## Residual risk — stated plainly

While the Puter SDK **is** loaded in the page, a malicious copy of it could still
read the token from the page (it is in the DOM and in memory). The changes above
mean that state is now opt-in and temporary rather than the default, but they do
not eliminate it.

The complete fix is to stop treating a long-lived bearer token as a browser
credential: the front end should exchange it once for a **short-lived, httpOnly,
SameSite session cookie** issued by the backend, so that no script on the page can
read a usable credential at all. That is a v0.21 architecture change. It is
recorded here so it is not mistaken for already-done.

## Also in this revision — the backend is now auditable

Doctrine requires the system to be auditable. It was not: a rejected credential,
a throttled caller, and a Letta failure were indistinguishable from outside —
they all produced nothing.

v0.20.5 emits one JSON object per line on stdout (the only durable record on a
free Render instance) for `config_check`, `auth_denied`, `rate_limited`,
`message_sent`, `session_created`, and `agent_created`. Reads are not audited.
No token, key, message body, or Letta error payload is ever written. Every
response carries an `X-Request-ID` that appears on the matching audit line.

Verified at runtime:

```
{"agent_pinned": false, "allowed_origins": [], "checks_failed": [], "event": "config_check",
 "frontend_dir": "frontend", "model": "letta/auto", "ok": true,
 "service": "oddfellow_letta_backend", "ts": "2026-09-30T02:21:57Z", "version": "0.20.5"}

{"event": "auth_denied", "method": "GET", "origin": "https://example.test",
 "path": "/api/letta/status", "reason": "no_token", "request_id": "47e6dd092814", …}
```

Set `ODDFELLOW_AUDIT_LOG=false` to silence it.

# Addendum 2026-10-01 08:05 UTC — the vulnerability is in the DEPLOYED service worker, latent not live

Checked the live artifact rather than the branch, because the deployed front end is
commit `91b411c` and predates the fix. **The vulnerable pattern is deployed.**

`https://oddfellow-letta-ui-v020-pwa.onrender.com/sw.js` (782 B, fetched live):

```js
if(url.origin!==self.location.origin)return;   // never cache API or third-party calls
e.respondWith(fetch(e.request).then(r=>{
  const copy=r.clone();
  caches.open(CACHE).then(c=>c.put(e.request,copy)).catch(()=>{});
  return r;
})...);
```

The comment says *"never cache API or third-party calls."* **The code implements
something weaker: "never cache cross-origin."** Those are the same thing only while
the API happens to live on another origin. `caches.put` is called unconditionally
for every same-origin GET.

## Why it is latent rather than live right now

In the **current two-service deployment** the API is on a *different* origin
(`oddfellow-letta-poc.onrender.com`) from the page
(`oddfellow-letta-ui-v020-pwa.onrender.com`). The origin check therefore does
exclude `/api/*`, and authenticated responses are **not** being cached today.

**So the deployed site is not currently leaking anything.** That is worth stating
plainly rather than reporting a live breach.

## Where it becomes live

It becomes live the moment the page and the API share an origin — which is exactly
what the **single-service** deployment does, and why the fix exists. The combined
branch carries the fix (`c468757`), so that path is safe.

**The residual risk is a branch combination, not a running service:** deploying
same-origin mode from a branch that has the front end but *not* the service-worker
fix would put this live. The guard is the fix in the tree, not the deployment shape.

## The transferable point

This is a check whose condition could not vary. The comment asserted a property the
code did not implement, and the deployment shape made the assertion *look* true. A
reviewer reading the comment, or testing only the deployed two-service layout, would
conclude the worker was safe — correctly, and for the wrong reason.

**A comment is not a control.** When a security property matters, verify the code
implements it rather than that the current environment happens not to exercise it.
