# `oddfellow-letta-backend-v0206` returned 502 for a sustained window — 2026-10-14

**Observed:** 2026-10-14 22:02–22:07 UTC · **Status: service unavailable (502), self-resolved or not yet confirmed**

## What was measured

| Probe | Result |
|---|---|
| 5 consecutive `/livez` probes over ~3 min | **`502` × 5**, each in ~0.2s |
| Response body | Render's own **"502 Bad Gateway — This service is currently unavailable"** page, Request ID `a4a9ddd3c8b73451-PDX` |
| Last hour (21:00–21:18 UTC) | **`000`** at 120s *and* 300s, then recovered by itself at 21:18 |

**A 502 in 0.2s is Render's edge answering — not a slow backend.** The edge is healthy; there is no
healthy instance behind it.

## Scope — this is not Render, and not the network

| Service | Result |
|---|---|
| `oddfellow-letta-ui-v020` | **200** in 0.22s ✅ |
| `oddfellow-personal-v019` | **200** in 0.20s ✅ |
| `begg-ai-core` | **502** |
| `oddfellow-letta-backend-v0206` | **502** |
| `render.com` (control) | **200** in 0.16s ✅ |

**Two of our services answer `200` throughout while two return `502`.** That rules out a
platform-wide Render incident and rules out a network path problem from this sandbox.

## Why the two shapes matter, and are probably the same cause

| Shape | Meaning |
|---|---|
| **`000`** (last hour) | TCP connects, TLS completes, **no HTTP response at all** |
| **`502`** (this hour) | Render's edge **explicitly reports** the backend unavailable |

Both are the recorded signature of **"no healthy instance behind the router"**. The difference is
whether the edge got far enough to return its own error page.

**The earlier `000` was not a cold-start budget problem.** Two widenings (75s → 120s → 300s) failed
to produce a response, and the service then recovered on its own ~17 minutes later. **That is what
distinguishes "slow" from "absent": widening the budget does not help when nothing is there.**

## Not claimed

- **Not a platform outage** — two sibling services were healthy throughout.
- **Not a network fault** — the control and two of ours answered instantly.
- **Not diagnosed.** I can see *that* the backend has no healthy instance; I cannot see *why* from
  outside. No Render dashboard access, and the cause (crash loop, OOM, deploy, free-tier
  suspension) is not distinguishable from these observations.
- **No recovery action taken or needed.** The rehearsal is restored and passing; the Render service
  is the owner-deployed one and auto-deploy is OFF.

## What would make this actionable

**Repetition.** If the target keeps cycling in and out, that is a pattern worth an owner look at the
Render dashboard (which is where the actual cause is visible). One window that self-resolved last
hour plus a sustained 502 now is **two observations, not yet a trend.**

## Rehearsal unaffected

The local rehearsal was restored and **all acceptance gates pass** (Gates 0–3). The rehearsal is a
separate process on this sandbox and does not depend on the Render service being up.
