## 6. 🔴 The blocker I found, and the fix I shipped

**The deployed PWA is aimed at the one backend that will not answer it.** The live
page carries:

```js
const DEFAULT_BACKEND_URL='https://oddfellow-letta-poc.onrender.com';
```

and I re-probed `oddfellow-letta-poc` with
`Origin: https://oddfellow-letta-ui-v020-pwa.onrender.com`:

```
HTTP/2 200        <- and NO access-control-allow-origin header
```

So the browser will reject the response. The only deployed front end that *can*
reach a backend is pointed at the one backend that CORS-rejects it — the same
failure class as the 01:38 UTC finding, with a different pair of URLs. **Setting
secrets on `oddfellow-letta-poc` would not have fixed this.**

**Diagnosed the `update_failed`.** Two things each correct alone collide:
`/healthz` fails closed with 503 when a required env var is missing, and Render
treats a non-200 `healthCheckPath` as a **FAILED DEPLOY**. Together they reported
"the secrets have not been entered yet" as "the build failed" — indistinguishable
from outside, which is exactly the state I was looking at.

**Fix shipped:** `GET /livez` — always 200 while the process is up, carrying `ready`
and `checks_failed` in its body. `render.yaml` now sets `healthCheckPath: /livez`.
**`/healthz` is unchanged**: still 503, still the readiness gate for humans and for
the acceptance harness. A deploy can no longer fail its health check over a missing
secret, and the truth is still one request away.

Also shipped: `ALLOWED_ORIGIN` now includes the PWA origin (it was the missing one);
the PWA front end is repointed at `oddfellow-letta-backend` and carries the token fix.

## 7. Security issues discovered

1. **Owner-token exposure in the front end (fixed in v0.20.5, not yet deployed).**
   The token was written to `localStorage` while `https://js.puter.com/v2/` — a
   third-party script — ran in the same origin and could read it, on every load,
   with no user action. The token authorises reading the owner's history and
   sending messages as the owner. Now: the SDK is lazy-loaded (never loaded at all
   once a backend is configured) and the token is memory-only unless explicitly
   opted in. **The deployed PWA still has the old behaviour** — it is `91b411c`.
   Residual, stated plainly: while the SDK *is* loaded it could still read the
   token from the page. The complete fix is a short-lived httpOnly session cookie
   (v0.21). Full write-up: `oddfellow/SECURITY-2026-09-30.md`.
2. **The backend was not auditable.** A rejected credential, a throttled caller,
   and a Letta failure all produced nothing. It now emits one JSON object per line
   on stdout for `config_check`, `auth_denied`, `rate_limited`, `message_sent`,
   `session_created`, `agent_created`. Reads are not audited. No token, key,
   message body, or Letta error payload is ever written.
3. **Letta's two agent read paths return disjoint sets.** `POST /v1/agents/search`
   lists the two junk agents but **not** the pinned Oddfellow agent; `GET
   /v1/agents/{id}` reads the pinned agent but **404s an agent search just
   returned**. Neither path can prove an agent does not exist. `resolve_agent()` is
   correct to prefer the pinned id — please do not "fix" it to trust search.
4. The sandbox `LETTA_API_KEY` can read the pinned agent, so it would technically
   serve the backend — but it is a platform-managed key the owner cannot rotate.
   **Use the owner's own key.**
